## MODIFIED Requirements

### Requirement: Added and modified requirements carry an executable check

`scripts/spec-change.py links --base <rev>` SHALL compare the files under `openspec/specs/` at `<rev>` and at `--head` (default `HEAD`). For every requirement that is new or whose text differs between the two, it SHALL require one of two things: at least one `##### Example:` under the requirement, where each such Example has a title that is unique within its capability and a tracked file at the head revision, outside `openspec/` and not ending in `.md`, that contains the marker `spec-example: <capability> / <Example title>` (a tracked file of a submodule counts, as the paragraph "Submodules" below describes); or a line under the requirement that starts with `No executable check:` followed by a reason. A requirement that does not differ SHALL NOT be checked. A marker counts only when nothing but whitespace, or the comment closer `-->` or `*/`, follows the Example title on its line. Lines inside a code fence are not read as `##### Example:` or `No executable check:` lines; a fence opened by three or more backticks or tildes, at any indentation (as inside a list item), closes only on a line of the same character, at least as long, with nothing but whitespace after it; lines end only at `\n`, `\r\n` or `\r`. A requirement heading indented by up to three spaces SHALL be read as a requirement, as Spectra reads it. Paths SHALL be read as git stores them, never in git's quoted form, so a capability whose directory name is not ASCII is checked like any other. Two requirements with the same name in one capability SHALL make the command print `error`. So SHALL a code fence at the head revision that never closes, since the requirements after it would go unchecked. Outside code fences, a heading that starts with `### Requirement` but does not have the form `### Requirement: <name>` with a non-empty name SHALL make the command print `error`, and so SHALL a head revision at which the spec directory's `specs/` holds no tracked file, and a path under the spec directory's `specs/` that is not valid UTF-8 (the reason says so and carries no text of an exception). Such a path elsewhere under the spec directory does not change the answer. The command SHALL print one JSON line with `status` (`ok`, `missing` or `error`) and a list naming each requirement or Example that lacks its check, and SHALL exit 0, 1 or 2 in that order. `--base` is required: the caller names the range, so that a run on the default branch is checked against the commit it started from. The marker ties an Example to a test by name only; whether the test exercises what the Example states is judged by the reviewers of `idd-verify`.

Submodules. The tracked files at the head revision include the tracked files of every submodule of the repository at the commit that the head revision records for it, and in the same way the files of a submodule of a submodule. The command SHALL read that recorded commit, not the commit the submodule's working tree is on. It SHALL find the submodules itself, from the entries of the head revision's tree that record a commit; it SHALL NOT rely on git's own recursion into submodules, which passes over a submodule that is not checked out without saying so; the answer SHALL be the same whether or not the git configuration turns that recursion on (`submodule.recurse`). A file of a submodule is named by the submodule's path followed by the file's path, and the two exclusions (under the spec directory, ending in `.md`) apply to that name. A submodule whose own path is under the spec directory SHALL NOT be searched and SHALL NOT count as one that could not be searched: none of its files could count. Nor SHALL a submodule be searched, or count as one that could not be searched, when its directory, after symbolic links are resolved, is the spec directory of the main repository or lies under it, whatever its path is named: a symbolic link, or another spelling of the name on a volume that does not distinguish letter case, can lead into the spec directory from a path that is not under it by name. This is decided after conditions 1 and 2 of the paragraph "Which submodules can be searched" below, and in the way of condition 2: the spec directory is one of the directories passed before the top directory is met, and directories are compared, not names. A spec directory that cannot be examined has nothing under it.

Order of the search. For each Example the command SHALL search the main repository first. When the marker is found there, the Example has its check and the command SHALL NOT run git in any submodule for it, so for a repository whose markers are all in its own files no entry that records a commit is listed and no submodule is examined, whatever its head revision records. Only when the marker is not found in the main repository are the submodules searched, and a marker found in one submodule settles the Example whatever the state of the others. When the marker of an Example is found, the Example has its check, whether or not every submodule could be searched. The submodules inside a submodule are read from a listing of every tree of its recorded commit, and that listing is made only when the outer one meets its own six conditions. Each of them is then searched whenever its own six conditions hold, also when the search of the outer one failed. When the listing fails, because a tree of the recorded commit cannot be read, the submodules inside it are unknown, even when the top tree shows them.

Which submodules can be searched. A submodule SHALL be searched only when all six of these hold: (1) its path, as the tree records it, is relative and has no empty, `.` or `..` component; (2) its directory, after symbolic links are resolved, is the top directory of the main repository or lies under it, which means that the top directory is met when going from the resolved directory to its parent directory, to the parent of that one, and so on; and no directory passed before the top directory is met (the resolved directory itself, unless it is the top directory, and each directory between the two) is one of two directories, the one that `git rev-parse --absolute-git-dir` prints and the one that `git rev-parse --git-common-dir` prints when run at the top directory (in a linked worktree these are two different directories); (3) the directory itself is not a symbolic link; (4) the directory holds an entry named `.git` of its own; (5) git, run in the directory, reports that same directory as the top of its own working tree; (6) its object store holds the recorded commit. In conditions 2 and 5 directories are compared, not names: two paths name the same directory when the operating system reports the same device and the same inode for both, however each path is spelled (on a volume that does not distinguish letter case, for one, a path written in another letter case names the same directory). A directory on the way up that cannot be examined (one that does not exist, for one) is passed over: it is neither the top directory nor one of the two. The two directories of condition 2 are a closed list: no other directory is refused under that condition. No git directory of a submodule is added to the list: when the git directory of a submodule is itself one of the two, or lies under one of them, condition 2 applies to it as written, and otherwise a directory inside it is searched when the six conditions hold. The top directory is not compared with the two, so when the top directory is one of them, or lies inside one of them, neither it nor the directories under it are refused for that reason. A directory that resolves to the top directory itself meets condition 2. The command SHALL NOT run git in a directory that fails any of the first four: a directory of ordinary tracked files can be shaped like a git directory, and git would read, and act on, the configuration it holds. Nor SHALL it run git in the directory of any submodule when git is older than 2.45, the first version that honours `GIT_NO_LAZY_FETCH`, or when the version cannot be read: a submodule for which the first four hold then counts as one that could not be searched. In the directory of a submodule the command SHALL run git with `safe.bareRepository` set to `explicit`, with lazy fetching turned off (`GIT_NO_LAZY_FETCH=1`), and with the variables `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` and `GIT_COMMON_DIR` removed from the environment it inherited. Before it searches a submodule the command SHALL ask git which objects of the recorded commit (its trees and the contents of its files) the object store lacks or cannot open, without fetching any: an object whose file is present but cannot be opened (for example an empty file) counts as lacking. A submodule is searched even when some are lacking, and a file that counts, found by a search that ran to its end (exit code 0 or 1), settles the Example. What a search printed before it ended with another exit code SHALL NOT be used, so that the answer for one state of the repository is the same on every run. When no file that counts is found in it, the submodule counts as one that could not be searched if its object store lacks an object of the recorded commit, if the search exits with a code other than 0 or 1, or if the trees of the recorded commit cannot all be listed. What git writes to its error stream SHALL NOT change whether a submodule counts as searched, nor the reason reported for it. In the main repository a search that exits with a code other than 0 or 1 is `error`, as before; its reason is `git grep failed: ` followed by the first 200 characters of what git wrote to its error stream, also as before.

What is reported. When the marker is not found and every submodule was searched, the Example is reported as lacking its check, as before. When it is not found and at least one submodule could not be searched, the command SHALL print `error` and name the first such Example it meets, the submodules that could not be searched and the reason for each: an Example whose candidate files were not all read is not reported as lacking its check. The submodules are named by path, in the order of their paths and joined by `; `; a submodule of a submodule is named by its path under the outer one; when more than five could not be searched, the first five are named and the number of the others is stated; a path longer than 200 characters is cut to its first 200 followed by `...`. The reason is one of six: the path leaves the repository (conditions 1 and 2); the submodule is not checked out (conditions 3 and 4, or git names another directory as the top); git is older than 2.45 (stated also when its version cannot be read); git refused to open it (the git command of condition 5 fails); the recorded commit is not in its object store (condition 6); the recorded commit could not be read (its object store lacks or cannot open an object of it, or the search or the listing of its trees failed). The reason given for a submodule SHALL NOT carry text from git's error stream. The path of a submodule that is not valid UTF-8 is handled like any other path, and the command still prints one JSON line. A repository whose head revision records no submodule is searched in its own tracked files only: none of the rules for submodules changes its answer.

#### Scenario: An Example without a test is reported

- **GIVEN** a range that adds a requirement with one Example titled `status by exit code` to the capability `local-ci-gate`
- **AND** no tracked file outside `openspec/` contains `spec-example: local-ci-gate / status by exit code`
- **WHEN** `spec-change.py links` runs on that range
- **THEN** it prints `status` `missing`, names that Example, and exits 1
